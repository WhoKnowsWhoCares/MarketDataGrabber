# MarketData — Спецификация проекта

Личная система сбора рыночных данных через T-Invest API (Т-Банк): накопление истории, аналитика, торговые сигналы и рекомендации пользователю с возможностью полуавтоматического исполнения.

## Problem Statement

**Как нам построить систему, которая непрерывно собирает рыночные данные (цены, объёмы, характеристики) через T-Invest API, хранит их в аналитической БД в пригодной для анализа/ML форме и превращает их в проверяемые торговые сигналы и рекомендации?**

Целевой пользователь — сам владелец (личный инструмент). Решения о сделках принимает человек; система готовит данные, отчёты и сигналы, с фазы P6 — исполнение по кнопке.

## Recommended Direction

**«Фундамент сначала»**: данные → отчёт → сигналы → бэктест → полуавтомат. Каждый этап строится на готовом предыдущем. Первая видимая ценность (Telegram-отчёт) приходит на P3, после устойчивого сбора данных.

## Подтверждённые возможности T-Invest API

- **`GET /history-data?instrument_id=...&year=YYYY`** — ZIP-архив **минутных свечей за год** по инструменту одним запросом. Обновляется раз в сутки, текущего дня нет. Поля: UID, UTC, open, close, high, low, volume (в лотах). Бэкофилл истории — архивами, не поллингом.
- **`GetCandles`** — свечи 1м/2м/3м/5м/10м/15м/30м/1ч/2ч/4ч/день/неделя/месяц. Лимит на запрос: минутки — 2400 свечей (~1 торговый день), дневки — до 6 лет.
- **Стриминг `MarketDataStream`** — двунаправленный gRPC-поток: свечи, стакан, сделки, ласт-прайс в одном соединении.
- **События и фундаментал (родные методы):** `GetDividends` (экс-дивидендные даты, суммы, доходности), `GetAssetReports` (**расписания выхода отчётностей эмитентов**), `TradingSchedules` (календарь сессий и праздников), `expiration_date` фьючерсов, `GetInsiderDeals`, `GetConsensusForecasts`, `GetBondCoupons/Events`.
- **Тех. индикаторы** — есть готовый endpoint у Т-Банка.
- **Песочница (sandbox)** — бумажная торговля для обкатки заявок.
- **Python SDK** — официальный `tinkoff-investments`; при несовместимости с системным Python 3.14 — raw gRPC по публичным proto.
- Точные лимиты запросов зависят от тарифа — **проверить после получения токена**.

## Гранулярность данных (решено)

Два независимых атомарных зерна, live — отдельно:

| Слой | Данные | Хранение |
|---|---|---|
| **1m (атом)** | минутные свечи: архивы `/history-data` + ежедневный инкремент | ClickHouse, raw, постоянная история |
| **1d (атом)** | дневные свечи напрямую из `GetCandles` (история до 6 лет) | ClickHouse, raw, независимо от 1m |
| **Промежуточные ТФ** | 5m/15m/1h/4h/W/M | **не храним** — материализованные представления поверх 1m |
| **Дневной слой фич** | OHLCV(день) + VWAP, ATR, объём vs MA, RSI, MA | расчёт после закрытия, готовые фичи для сигналов/ML |
| **События** | events(event_time, type, instrument_id?, importance, expected/actual, source) | отдельная таблица + фича «дней до события» |
| **Live** | стриминговые свечи/стакан/сделки | **отдельное хранилище, история ~1 день** (TTL), затем консолидация в 1m |

Принципы:
- 1m и 1d считаются независимо: дневная история старше минутных архивов, конвенция границ дня не влияет на 1d.
- Промежуточные ТФ — только представления: один источник истины, ноль расхождений.
- Point-in-time гигиена: `expected_date` (для фичи «дней до события») и `actual` храним отдельно.
- Объём: минутки ≈ 1,1 тыс. свечей/день на инструмент (год ≈ 280K строк × 5 инстр.) — ничто для ClickHouse; стакан в 1000+ раз тяжелее — потому TTL на live.

## События (календарь)

| Источник | События | Режим |
|---|---|---|
| T-Invest `GetDividends` | экс-дивидендные даты, суммы, доходности | по расписанию (ежедневно/еженедельно) |
| T-Invest `GetAssetReports` | расписания отчётностей эмитентов | еженедельно |
| T-Invest `TradingSchedules` | сессии, праздники, режимы | еженедельно + проверка ежедневно |
| T-Invest инструменты | `expiration_date` фьючерсов | при появлении новой серии |
| **Внешний агрегатор** (Investing.com / Finam — источник зафиксировать при реализации) | макрокалендарь: ставка ЦБ, Росстат (ИПЦ/ВВП), FOMC, CPI и пр. | **скрейпинг раз в неделю по выходным**; схема event-таблицы source-агностична, чтобы источник можно было заменить |

## Фундаментальный слой (решено)

Только для акций (SBER, GAZP); фьючерсы — без фундаментала.

| Таблица | Источник | Что храним | Режим |
|---|---|---|---|
| `fundamentals_snapshot` | `GetAssetFundamentals` (до 100 активов за запрос) | Полный снапшот ~50 полей: P/E, P/S, P/B, EV/EBITDA, EV/Sales, FCF, ROE/ROA/ROIC, маржи, долги (Debt/EBITDA, Debt/Equity), рост выручки 1/3/5 лет, капитализация, shares outstanding, free-float, бета, 52w high/low, ADV, дивидендные метрики (DY ttm/forward/5y, payout, buyback), employees | **снапшоты ежедневно после закрытия** — историю API не отдаёт, накапливаем свою point-in-time историю |
| `dividends` | `GetDividends` | ex-dividend date, размер на акцию (`dividend_net`), тип (Regular/Cancelled), DY, close price на ex-date | еженедельно |
| `reports` | `GetAssetReports` | даты публикации отчётов + период (год, номер, тип: квартал/год) — расписание и факты | еженедельно |
| `forecasts` | `GetConsensusForecasts` + `GetForecastBy` | консенсус: целевая цена 12м (min/target/max) → **ожидаемая доходность** = target/price−1; прогнозы инвестдомов: рекомендация (buy/hold/sell), цель, дата | еженедельно; point-in-time через `created_at`/`recommendation_date` |
| `company_profile` | InstrumentsService | название, сектор, ISIN, валюты, лот, country — медленно меняющийся справочник | при изменениях |

Производные фичи: «P/E vs медиана сектора», «дней до отчёта», «дней до ex-dividend», «имплицитная ожидаемая доходность».

Ограничение: поквартальные цифры отчётности (выручка/прибыль за квартал) API не отдаёт — только TTM-значения в снапшотах. Если понадобится — MOEX ISS, позже.

## Стек и инфраструктура (docker compose, решено)

Всё в отдельных сервисах одного `docker compose` с профилями (core/obs/bot/live) — можно поднимать группами; масштабирование = вынос сервиса в отдельный хост.

```
profile core:
  clickhouse        # 1m, 1d, events, fundamentals; live — отдельная БД в нём же с TTL ~1 день
  scheduler         # APScheduler: DAG дня fetch → clean → marts → dq → notify + еженедельные задачи
  collector-daily   # инкремент свечей + снапшот GetAssetFundamentals (после закрытия)
  collector-weekly  # события: дивиденды, отчётности, TradingSchedules, экспирации, консенсус
  scraper-macro     # еженедельный скрейпинг агрегатора макрокалендаря (выходные)
  watchdog          # staleness-проверки пайплайна и витрин (по etl_runs)
profile obs:
  grafana           # дашборды + алерты
  loki + promtail   # центральное хранилище логов (ретенция ~30 дней)
profile bot:
  telegram-bot      # отчёты и рыночные сигналы (P3), кнопки исполнения (P6); aiogram
  redis             # cooldown алертов, pending-подтверждения сделок (TTL), кэш словарей
  sqlite (volume)   # конфиги: users, subscriptions, quiet hours
profile web (позже):
  api               # FastAPI: бэкенд HTML-страницы (/candles, /fundamentals, /signals) + админ-эндпоинты
profile live (P6):
  streamer          # gRPC-стрим → live-БД, стакан 1/мин
```

Гигиена: `.env` вне git, chmod 600; три секрета с P0: токен read-only, trade-токен (только P6), токен бота (BotFather). Сети внутренние, наружу только Grafana на 127.0.0.1. `restart: unless-stopped`, healthchecks, образы pinned. Ориентир RAM: ~3–4 ГБ на весь стек.

### Оповещения (решено: две категории с первого дня)

| Категория | Что | Получатели | Маршрут |
|---|---|---|---|
| **ops** (технические) | staleness, падения сборщиков, контейнеры, диск | **только админ** — приватный чат, chat_id из env; никогда не проходит через подписки | watchdog + Grafana → бот |
| **market** (рыночные) | сигналы, дайджесты, события (отчёт, ex-dividend, экспирация) | диспетчер подписок; сейчас только админ, **потом другие пользователи** | таблица `subscriptions` → бот |

- `subscriptions(user, chat_id, instrument?, signal_type?, min_importance?, quiet_hours?)` — SQLite; добавление пользователя = INSERT, без изменения кода.
- Анти-спам: cooldown в Redis — одинаковый сигнал по инструменту не чаще раза в N часов (per user × signal × instrument).
- Общий диспетчер нотификаций — shared-пакет монорепо; все сервисы отправляют через него, прямой вызов Telegram API из коллекторов запрещён.

### Стек приложений (решено)

- **Python 3 везде.** Общий код (конфиг, ClickHouse-клиент, T-Invest клиент, диспетчер нотификаций) — shared-пакет; сервисы — тонкие точки входа.
- **FastAPI** — только там, где есть HTTP: сервис `api` (бэкенд HTML-страницы + `/health`, админ-эндпоинты). Появляется с веб-профилем; коллекторы — batch-джобы без HTTP.
- **aiogram** — телеграм-бот (async); графики в отчётах — matplotlib/plotly → картинки.
- **Redis** — не с P0: с профиля bot (P3) — cooldown и кэш; к P6 — pending-подтверждения сделок `pending_order:{id}` с TTL ~60 сек (кнопка «исполнить» действует ограниченное время).

### Наблюдаемость (решено)

1. **Логи приложений:** структурированный JSON в stdout (service, stage, instrument, error); секреты маскируются; сбор — Promtail из Docker в Loki, ретенция 30 дней.
2. **Watchdog (главный алерт):** по расписанию проверяет свежесть данных в ClickHouse — «свечи не обновлялись N часов», «упал инкремент/снапшот» → Telegram (топик ops).
3. **Grafana-алерты:** контейнер умер/рестарт-петля, диск >80%, всплеск ошибок в Loki → Telegram.
4. Prometheus/cAdvisor — не на старте, при необходимости позже.

### Визуализация (решено)

- **Сейчас:** Grafana + ClickHouse-плагин: свечи/объёмы/мультипликаторы/консенсус, логи (Explore), алерты — всё в одном окне; дашборды хранятся как JSON в git (provisioning).
- **Позже:** своя HTML-страница (лёгкий FastAPI + plotly) под кастомный UX — отдельным сервисом в том же compose.

## Слои обработки данных (медальон, решено)

| Слой | Содержимое | Инструменты |
|---|---|---|
| **🥉 Bronze** | сырьё append-only: 1m, 1d, снапшоты фундаментала, события — с метаданными (fetched_at, source); ничего не правим руками | collectors → ClickHouse |
| **🥈 Silver** | нормализация (instrument_uid, UTC+MSK, лоты→штуки), дедупликация свечей (ReplacingMergeTree), валидация OHLC, выбросы → флаги, сверка дыр с торговым календарём, брак → карантин | идемпотентные SQL (INSERT SELECT) |
| **🥇 Gold (витрины)** | см. таблицу витрин ниже | SQL MV + INSERT SELECT |
| **ML-экспорт** | билдер датасетов `ml_features_daily` → parquet | Python (polars), P5+ |

### Витрины (gold)

| Витрина | Для чего |
|---|---|
| `mart_candles_tf` | 5m/15m/1h/4h/W/M — MV поверх 1m (Grafana, бэктест) |
| `mart_daily_metrics` | доходности 1/5/20d, ATR/волатильность, объём vs MA20/60, гэпы, позиция в 52w-диапазоне |
| `mart_indicators` | RSI, MA-кроссы, пробои, VWAP — предрасчитанные, point-in-time корректные |
| `mart_fundamentals_ts` | снапшоты → временные ряды мультипликаторов + перцентили |
| `mart_events_features` | события → «дней до/после» на инструменто-день |
| `ml_features_daily` | широкая таблица фич + labels (форвардные 1/5/20d) — тренировочный сет |

### Правила

1. **Идемпотентность:** трансформ перезапускаем на диапазон дат (delete+insert по партиции) — бэкофилл витрин = тот же код.
2. **Point-in-time:** в `ml_features_daily` фичи — только известное на конец дня D; labels — отдельные колонки, в фичи не подмешиваются.
3. **Lineage:** `etl_runs(transform, date_range, rows_in/out, errors, duration, code_version)`; `dq_metrics` + карантин; watchdog алертит «витрина не обновилась».
4. **Grafana читает только gold.**
5. **DQ — отдельные шаги пайплайна** (не inline SQL): флаги + карантин + алерт, пайплайн продолжается.

### Оркестрация (решено)

- Сервис **`scheduler`** (APScheduler, профиль core) — DAG дня в Python-файле в репо: `fetch → clean → marts → dq → notify` + еженедельные задачи; ретраи, etl_runs, алерты.
- Трансформации — SQL-файлы в репо + тонкий Python-раннер; dbt не на старте (триггер: 15+ моделей / приход оркестратора).
- **Триггеры апгрейда стека:** очередь (Redpanda) — при полном рынке + тиковом логе или нескольких потребителях; Airflow/Prefect — при >10–15 задач или втором человеке.

## Фазы

- **P0. Пререквизиты:** токен read-only Т-Инвестиции, токен бота (BotFather), git-репо, скелет docker compose (clickhouse + grafana/loki/promtail), схема хранения (1m, 1d, events, fundamentals, live), проверка лимитов и SDK на Python 3.14.
- **P1. Бэкофилл:** годовые архивы минуток по 5 инструментам + дневные свечи `GetCandles` → bronze; отчёт о дырах; проверка конвенции вечерней сессии и расхождений 1m vs 1d.
- **P2. Инкремент + витрины:** ежедневный DAG в scheduler (fetch → silver clean → gold marts → dq → notify); обновление свечей всех ТФ после закрытия/клиринга; ежедневный снапшот `GetAssetFundamentals`; сбор родных событий (календарь сессий, дивиденды, экспирации, отчётности, консенсус-прогнозы); silver/gold трансформации + `etl_runs`/`dq_metrics`, DQ-шаги с карантином.
- **P3. Отчёт:** Telegram-дайджест по universe (цена, объём vs средний, ключевые индикаторы, P/E и другие мультипликаторы, ожидаемая доходность по консенсусу, ближайшие события — отчёты и ex-dividend); Grafana-дашборды (свечи, объёмы, фундаментал) + алерты obs-профиля; бот: разделение ops/market, таблица подписок (пока только админ), redis-профиль (cooldown).
- **P4. Сигналы:** volume spike, пробой диапазона, MA crossover, RSI — с частотной валидацией на истории; макрокалендарь (еженедельный скрейпинг) как контекст.
- **P5. Бэктест:** прогон сигналов по истории, оценка без lookahead bias.
- **P6. Полуавтомат + live:** trade-токен, inline-кнопки «исполнить» с pending-подтверждением в Redis (TTL ~60 сек), guardrails (лимиты суммы, только chat_id владельца); live-стриминг с отдельным хранилищем ~1 день, сэмплирование стакана раз в минуту.
- **P7. Веб:** FastAPI-сервис `api` + HTML-страница (свечи, фундаментал, сигналы), админ-эндпоинты; мультипользовательские подписки на market-алерты с per-user фильтрами.

- **Своя HTML-страница в MVP** — Grafana закрывает визуализацию MVP; своя страница — отдельная фаза P7
